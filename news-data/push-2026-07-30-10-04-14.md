### Show HN: Open-source engine running Gemma 4 26B in 2 GB RAM on any M-series Mac

657 pts · 227 comments · [github.com/drumih](https://github.com/drumih)

**📌 内容总结**

- 作者用 Swift + Metal 构建了一个仅针对 Gemma 4 26B-A4B（MoE架构）的自定义推理引擎，核心思路是只加载共享权重和 KV 缓存（约 2 GB），其余专家权重通过 SSD 流式读取，缓存命中率约 67%。
- HN 关注点:
  - 性能数据：M2 MacBook Air (8 GB) 5–6 tok/s，M5 Pro (24 GB) 31–35 tok/s，差距主要来自 SSD 速度和可用内存量。
  - 工程实现：从 mmap 切换到 parallel pread 是最大加速来源（0.5 → 4 tok/s），GPU 与 I/O 重叠进一步优化。
  - 与 llama.cpp/MLX 对比：本引擎牺牲绝对速度换取极低内存占用，适合内存受限场景。

**💬 讨论总结**

- **共识观点**：该项目是工程技巧的体现——用 SSD 换内存，适合 8 GB Mac 用户。专家缓存机制（16 slots）实际有效，并非理论玩具。
- **工程经验**：OS 的 mmap 按需分页无法预知专家选择，parallel pread + GPU overlap 是更优策略。M5 SSD 读取速度（6.3 GB/s）是 M4（2 GB/s）的 3 倍，直接拉高 tok/s。
- **历史背景**：此前已有 Colibri、Flash-MoE 等项目实现类似 SSD 流式推理，本项目的贡献在于针对 MoE 的小型专家做了精细的 Metal 内核定制和缓存调度。
- **质疑/反对**：部分用户认为 5–6 tok/s 实用性有限，适合离线 / 低交互场景。另有人认为如果 RAM 足够（24 GB+），直接用 MLX 跑 75 tok/s 更划算。也有用户担忧 SSD 写入磨损，但实际只读取不写入。
- **商业现实**：Mac 统一内存昂贵，SSD 流式方案可能是低端设备本地推理的合理方向，但吞吐量受 SSD 带宽限制。

### Show HN: A local merge queue for parallel Claude Code agents

16 pts · 3 comments · [github.com/funador](https://github.com/funador)

**📌 内容总结**

- 作者想解决：当多个 Claude Code agent 同时工作时，如何防止 push 冲突、重复 build 和 test 竞争。做法是提供一个本地 FIFO merge queue（基于 git worktree），通过 `land` 命令串行化提交，并强制运行 check 命令。
- 技术实现：TypeScript 包，无运行时依赖，通过 `build-lock` 实现机器级锁，`pre-push` hook 阻止直接 push。支持紧急 bypass 环境变量。
- 产品设计：零成本（不上云），与 GitHub Merge Queue 功能对标但适用于单机 / 本地开发流程。

**💬 讨论总结**

- **共识观点**：想法合理，但实际场景有限——多数 CI 已能处理冲突重跑。本地方案受限于单机能力，无法横向扩展。
- **反对意见**：有用户推荐用 jj（Jujutsu）的 workspace 机制替代 git worktree，认为 jj 天然支持并行分支管理，更简洁。
- **工程经验**：本地锁依赖 PID 存活状态（非超时），避免竞态；rebase 冲突直接 abort 而非自动解决，留给 agent 重试。

### Document-borne AI worms can self-propagate through Copilot for Word

348 pts · 267 comments · [enklypesalt.com](https://enklypesalt.com/posts/context-collapse-part3-ai-worming-through-word/)

**📌 内容总结**

- 背景 / 作者意图：展示一种针对 Microsoft Copilot for Word 的攻击——攻击者将隐藏指令（白色文字、小字号）嵌入文档，Copilot 在生成/编辑时执行指令（例如篡改财务数字），并将完整指令复制到新文档，形成自传播的 AI 蠕虫。
- 关键要点：
  - 属于跨域提示注入（XPIA），文档既是攻击载体也是传播媒介。
  - 微软在 144 天协调期内部署了两次缓解（包括模型升级至 GPT-5.5），但该漏洞类别仍未根本修复。
  - 作者认为这是 LLM 架构缺陷：模型无法区分输入中的“指令”与“数据”，因为两者占据同一上下文窗口。
- 实际结论 / 限制：目前无客户侧完整缓解措施，只能靠用户警惕外部文档；根本修复需要架构级改变（目前不可行）。

**💬 讨论总结**

- **共识观点**：这是 LLM 的安全根基问题——指令与数据不分，等价于“SQL 注入 × 宏病毒”。几乎所有参与 LLM 上下文的产品都存在类似风险。
- **工程经验**：隐藏文本方式多样（白字、超小字体、被图片覆盖），预处理无法彻底清理，因为格式信息会被 LLM 忽略。检测攻击需要另一个 LLM，又引入同样问题（“LLMs all the way down”）。
- **历史背景**：类似攻击已有 Morris II（邮件助手演示），但这是首个在商业办公套件中实现文档自传播的公开案例。社区将其与 1990 年代宏病毒对比。
- **反对意见**：少数观点认为可通过严格输入过滤（剥离隐藏文本 / 只保留可见内容）缓解，但多数人指出这是猫鼠游戏，且 LLM 能理解语义等价变体。
- **风险 / 限制**：一旦传播，污染文档内部分布，溯源困难；外部共享的文档可能成为组织间传播链。作者指出微软的缓解只提升了门槛，未关闭漏洞类。

## 今日洞察

**AI蠕虫从理论走向实用，LLM架构根本缺陷暴露**  
Hacker News 展示的针对 Microsoft Copilot for Word 的攻击，用隐藏指令嵌入文档实现自传播（"AI worm"），引起 348 点讨论。关键在于：这并非新漏洞类型（跨域提示注入 XPIA 早有演示），而是首次在商业办公套件中实现文档到文档的自动复制。社区将其类比为 1990 年代宏病毒与 SQL 注入的结合——LLM 无法区分输入中的“指令”与“数据”，因为它们在同一个上下文窗口中共存。微软在 144 天协调期内部署两次缓解（包括升级到 GPT-5.5），但作者认为该漏洞类未根本修复。二阶影响：所有将 LLM 嵌入文档处理的产品（Google Docs、Notion AI 等）都暴露于类似风险；安全厂商将推出输入过滤/内容隔离方案，但架构级修复（分离指令与数据通道）短期不可行，因为会破坏 LLM 的灵活性。企业用户对外部文档的信任模型必须调整，尤其是财务、法律等敏感场景。

**Agent 工具的内存效率成为新竞争维度，SSD 带宽反成瓶颈**  
GitHub 上 jcode（今日 +640 stars）用 Rust 实现单会话仅 27.8 MB PSS，对比 Claude Code 386.6 MB，首帧渲染 14 ms vs 3.4 s。同日 HN 上的 MoE 推理引擎通过在 8 GB Mac 上用 SSD 流式专家权重实现 5–6 tok/s（Gemma 4 26B）。两个项目揭示同一个趋势：随着 Agent 多会话并发成为常态（Claude Code、Cursor Agent 等），内存和启动延迟的约束正从“能否运行”转向“能否大规模并行”。jcode 的语义记忆系统和共享内存池设计，以及 MoE 引擎的 parallel pread + GPU overlap，说明软件层面的内存/ I/O 优化可带来 1-2 个数量级的提升。二阶影响：低端设备（8 GB Mac、边缘端）不再被排除在 Agent 工作流之外，但吞吐量受 SSD 读取速度限制（M5 6.3 GB/s vs M4 2 GB/s 差距 3 倍），硬件 SSD 带宽将成为新性能锚点，倒逼设备升级或进一步优化缓存策略。
